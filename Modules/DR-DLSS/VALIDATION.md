## 游戏内验收

2026-10-03，维护者确认当前模块已经通过游戏内验收。此结果来自维护者实际使用反馈；编译和隔离测试结果另行记录。

以下为该版本的验收范围，供后续更新复验使用：

1. 加载 0.1.2.0 后，作者栏为 VintageVelvet；模型与挡位完整单行显示且间距充分，配置路径完整单行显示。列表提供游戏默认/K/L/M。

3. “刷新生效”和“写入并刷新生效”正常结束，恢复原窗口模式、位置、尺寸和最大化状态。另观察最小化或无效参数的失败提示。
4. 关闭并重新启动游戏，确认目标配置仍被实际读取。此项是主要验收条件。
5. 在外部修改 INI 后观察当前配置约一秒更新，且待选值不被覆盖；改变窗口分辨率时输出尺寸更新，当前配置中的渲染尺寸按倍率变化（例如 3840×2160、2.0 倍对应 1920×1080）。

最小化、无效参数等异常场景未提供逐项结果，不单独标记为已通过。

## 0.1.3.0 热切换修复候选

0.1.2.0 的验收后补充发现：切到 DLAA 并写入、刷新窗口后，INI 显示 1×，但 ReShade 效果画面仍异常。该步骤没有退出或重启游戏；配置解析和窗口恢复完成不能证明运行时倍率已改变。

源码对照确认此前遗漏了运行时桥接。旧桥接更新 OptiScaler 内存中的倍率和预设，并设置 DLSS 后端重建标记；窗口刷新不能替代这一调用。已核对的自定义桥接构建为 `0.7.7-pre9 (20260525_062754)`，SHA-256 `B4E6905A3D9D4DC483AC7BFA7D3EA89F0B466BB437A7BBD771127016C075D38E`。

候选恢复 K/L/M 与默认挡位的桥接请求，再执行窗口刷新；只写配置不调用桥接。界面将估算尺寸标为“配置渲染分辨率”。旧协议无法关闭模型覆盖，因此游戏默认仍通过保存配置后重启应用，不冒充已完成热切换。

旧服务端回复后立即断开且未排空，可能丢失回复。客户端预先等待回复，严格核对响应；set 发送后失去回执会报告结果未确认，不重复发送。[Windows 的断开说明](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-disconnectnamedpipe)明确指出断开时可能丢弃尚未读取的数据。

此候选的游戏验证未通过：桥接接受请求且 OptiScaler 内存中的比例为 1.000，但其实际运行尺寸仍显示 `1280×720 → 2560×1440（2.0）`；ReShade 重新加载也未恢复。该证据确认配置目标与实际输入不一致，不能认定 DLAA 已生效。

- **编译**：使用 DR 2.2.2.0 / Dalamud API 15 实际依赖构建成功，无编译警告。
- **桥接协议**：46 项隔离命名管道检查通过，覆盖命令顺序、K/L/M、save 0、文化区、进程验证、严格响应、断开、超时、取消、只读探测重试及默认模型拒绝；不向游戏发送 set/save。
- **真实服务连通**：只读检查核对服务端属于当前游戏进程；先发送后读取出现 EOF，预挂读取后三次 ping 均返回完整 `ok bridge-ready`。此检查只证明通信链路，不验证挡位实际应用。

## 0.1.4.0 尺寸重建修复候选

原窗口刷新按临时矩形的宽高请求一次尺寸变化，在无边框模式稳定后再明确设置显示器矩形并请求显示器宽高；0.1.3.0 临时阶段改用客户区宽高，并在无边框后直接转入原窗口状态恢复。候选恢复原版这两次显式尺寸请求，再恢复原模式、位置及最大化状态；最终恢复请求仍使用实际客户区宽高。所有游戏操作仍在框架更新线程执行，取消和异常仍尝试恢复。

OptiScaler 的后端重建会复制旧实例的渲染与显示尺寸，并不调用游戏的最佳输入尺寸查询。配置倍率变化必须由游戏重新查询、更新资源后才体现到实际输入。源码依据见 [输入尺寸查询](https://github.com/optiscaler/OptiScaler/blob/v0.7.7-pre9/OptiScaler/NVNGX_Parameter.h)和[后端重建](https://github.com/optiscaler/OptiScaler/blob/v0.7.7-pre9/OptiScaler/inputs/NVNGX_DLSS_Dx11.cpp)。

界面改为“配置目标”和“配置倍率”，桥接回复改为“桥接更新已提交”。这些状态不证明游戏实际应用。修复候选需要核对 OptiScaler 实际输入是否变为 `2560×1440 → 2560×1440（1.0）`；尚未通过游戏复验。

- **编译**：使用当前兼容依赖构建成功，无编译警告。
- **协议回归**：46 项隔离桥接检查通过；窗口流程经独立源码复核。上述检查不操作游戏窗口，不证明实际输入尺寸已改变。

实际运行尺寸通过 OptiScaler 菜单核对，模块显示明确标注的配置目标。现有桥接没有状态查询接口，当前版本不增加菜单尺寸读取。

## 0.1.4.0 崩溃报告与暂停分发

2026-10-03，点击“写入并刷新生效”后游戏崩溃。0.1.4.0 Release 已转为草稿，暂停公开下载；该候选未通过游戏验收。

日志确认先发生 DR 全模块卸载及重载，随后交换链变为 2432×1368，与 2560×1440 的 0.95 倍临时尺寸吻合。之后 CLR 通过 Environment.FailFast 终止进程，原因为调用了已被垃圾回收的 `AtkComponentBase.Delegates.Dtor` 回调。崩溃堆栈没有直接指向 WindowRefresh、RuntimeBridge 或 OptiScaler，日志也没有记录模块刷新各阶段的直接调用信息。

当前模块没有安装 GUI 析构 Hook。尺寸刷新可能触发了失效的 GUI 回调，但回调所属模块、卸载重载与本次崩溃的因果关系仍需定位，不能仅凭这些日志归因于某个组件。原始崩溃包和转储不上传仓库。

崩溃后重新启动游戏，OptiScaler 菜单显示实际尺寸 `2560×1440 → 2560×1440（1.0）`。维护者确认该截图来自重启之后；此结果证明保存配置可在启动时应用，不能证明热切换成功。恢复热切换分发前，必须在同一次游戏运行中确认实际输入尺寸随挡位变化，并验证窗口恢复与稳定性。

## 0.1.4.0 后续热切换与延迟反馈

已有转储完成离线分析，缺少完整托管堆，无法定位被回收的委托对象或具体 GUI 节点；未据此宣称已修复崩溃。

## 0.1.5.0 重复恢复精简构建

运行日志中，一次恢复 2560×1440 的 ResizeBuffers 调用与运行环境重建完成之间相隔约 15.9 秒；同期间 MotionFocus.fx 编译耗时 16.277 秒，编译完成后才继续重建。随后又发生同样 2560×1440 的 ResizeBuffers。结合 ReShade 6.6.1 在重置效果时等待编译线程结束的源码，可以解释此次长时间停顿的一项具体来源；不据此将所有卡顿或此前崩溃归为同一原因。

精简构建保留已成功触发热切换的临时尺寸与完整显示器尺寸请求。原模式已是无边框时跳过模式恢复的空等待；对最终恢复，只有实际矩形、完整 WindowPlacement 和交换链状态分别吻合时才省去对应操作。存在待处理尺寸请求时不跳过，必要的窗口模式、最大化与位置恢复仍保留。没有实际恢复操作时省去最后一次固定等待。原无边框且状态已经完全恢复的路径，固定等待可由 4.8 秒降为约 3.2 秒，不含游戏与 ReShade 内部耗时。

0.1.5.0 编译成功，无编译警告；独立源码复核未发现此改动的明确恢复路径退化。实际运行性能尚未验证，也未修复或排除 GUI 析构回调崩溃。不安装到运行中的游戏，不公开发布。

操作状态不再长期停留在“桥接更新已提交”：刷新期间不显示中间状态，只在结束时保留 ok applied 回执并显示窗口刷新完成或失败。“写入并刷新生效”只在流程结束后通知结果，单独“写入配置”仍通知保存结果。该反馈不声称测量了实际 DLSS 输入尺寸。
