5. 在外部修改 INI 后观察当前配置约一秒更新，且待选值不被覆盖；改变窗口分辨率时输出尺寸更新，当前配置中的渲染尺寸按倍率变化（例如 3840×2160、2.0 倍对应 1920×1080）。

## 0.1.3.0 热切换修复候选

0.1.2.0 验收后发现热切换问题：在同一次游戏运行中切到 DLAA、写入配置并刷新窗口，INI 已显示 1×，ReShade 效果画面仍异常。此时需要检查游戏实际使用的输入尺寸。

源码对照发现此前遗漏了运行时桥接。桥接负责更新 OptiScaler 内存中的倍率和预设，并请求重建 DLSS 后端；原流程只写入 INI 和刷新窗口，缺少这一步。参考材料和自定义桥接构建的识别信息见 [PROVENANCE.md](PROVENANCE.md)。

候选恢复 K/L/M 与默认挡位的桥接请求，收到回执后执行窗口刷新；单独写入配置仍只修改文件。界面将估算尺寸标为“配置渲染分辨率”。旧协议无法关闭模型覆盖，游戏默认保留为保存配置后重启应用。

旧服务端回复后立即断开且未排空，可能丢失回复。客户端预先等待回复，严格核对响应；set 发送后失去回执会报告结果未确认，不重复发送。[Windows 的断开说明](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-disconnectnamedpipe)明确指出断开时可能丢弃尚未读取的数据。

此候选的 DLAA 热切换未通过游戏验证：桥接接受请求，OptiScaler 内存中的比例已为 1.000，实际运行尺寸却仍是 `1280×720 → 2560×1440（2.0）`。重新加载 ReShade 后情况没有变化，游戏仍沿用原来的 2× 输入尺寸。

- **编译**：使用 DR 2.2.2.0 / Dalamud API 15 实际依赖构建成功，无编译警告。
- **桥接协议**：46 项隔离命名管道检查通过，覆盖命令顺序、K/L/M、save 0、文化区、进程验证、严格响应、断开、超时、取消、只读探测重试及默认模型拒绝。测试使用模拟服务端，没有向游戏发送 set/save。
- **真实服务连通**：只读检查确认服务端属于当前游戏进程。先发送后读取时出现 EOF；预先挂起读取后，三次 ping 均返回完整 `ok bridge-ready`。检查仅发送 ping，挡位应用结果由上述游戏测试记录。

## 0.1.4.0 尺寸重建修复候选

原窗口刷新按临时矩形的宽高请求一次尺寸变化，在无边框模式稳定后再明确设置显示器矩形并请求显示器宽高；0.1.3.0 临时阶段改用客户区宽高，并在无边框后直接转入原窗口状态恢复。候选恢复原版这两次显式尺寸请求，再恢复原模式、位置及最大化状态；最终恢复请求仍使用实际客户区宽高。所有游戏操作仍在框架更新线程执行，取消和异常仍尝试恢复。

OptiScaler 的后端重建会复制旧实例的渲染与显示尺寸，并不调用游戏的最佳输入尺寸查询。配置倍率变化必须由游戏重新查询、更新资源后才体现到实际输入。源码依据见 [输入尺寸查询](https://github.com/optiscaler/OptiScaler/blob/v0.7.7-pre9/OptiScaler/NVNGX_Parameter.h)和[后端重建](https://github.com/optiscaler/OptiScaler/blob/v0.7.7-pre9/OptiScaler/inputs/NVNGX_DLSS_Dx11.cpp)。

界面改为“配置目标”和“配置倍率”，桥接回复改为“桥接更新已提交”。当时的复验目标是在同一次运行中切到 DLAA，并确认 OptiScaler 实际尺寸变为 `2560×1440 → 2560×1440（1.0）`。

- **编译**：使用当前兼容依赖构建成功，无编译警告。
- **协议回归**：46 项隔离桥接检查通过，窗口流程完成独立源码复核。游戏窗口和实际输入尺寸另行实测。

实际运行尺寸通过 OptiScaler 菜单核对，模块显示配置目标。现有桥接缺少状态查询接口，模块暂时无法读取菜单中的实际尺寸。

## 0.1.4.0 崩溃报告与暂停分发

2026-10-03，维护者点击“写入并刷新生效”后游戏崩溃。0.1.4.0 Release 随后转为草稿，暂停公开下载。

日志确认先发生 DR 全模块卸载及重载，随后交换链变为 2432×1368，与 2560×1440 的 0.95 倍临时尺寸吻合。之后 CLR 通过 Environment.FailFast 终止进程，原因为调用了已被垃圾回收的 `AtkComponentBase.Delegates.Dtor` 回调。崩溃堆栈没有直接指向 WindowRefresh、RuntimeBridge 或 OptiScaler，日志也没有记录模块刷新各阶段的直接调用信息。

当前模块没有安装 GUI 析构 Hook。尺寸刷新可能触发了失效的 GUI 回调，但日志缺少回调所属模块和节点的信息，尚无法还原委托失去引用、原生节点继续调用它的过程。DR 卸载重载与崩溃的关系仍待定位。

崩溃后重新启动游戏，OptiScaler 菜单显示实际尺寸 `2560×1440 → 2560×1440（1.0）`。维护者确认截图来自重启之后，记录的是保存配置在启动时生效。接下来的复验改为在同一次运行中切换挡位，同时检查实际尺寸、画面和窗口恢复。

## 0.1.4.0 后续热切换与延迟反馈

同日，维护者继续使用 0.1.4.0，在重启后的同一次游戏运行中完成 2.0 → DLAA 和 DLAA → 2.0 双向热切换。普通运行中的热切换已有成功反馈；此前崩溃发生前还经历了 DR 全模块重载，这一场景需要单独排查。维护者也怀疑模块重载与崩溃有关，具体失效的回调仍未找到。

维护者同时报告点击“写入并刷新生效”后画面长时间卡住。0.1.4.0 有六次固定等待，默认合计 4.8 秒，通过框架回调推进。画面停顿还涉及游戏和 ReShade 的资源重建耗时，需要结合运行日志检查。当时发布仍暂停，PR 保留草稿。

转储已完成离线分析，但没有完整托管堆，无法从中找到被回收的委托对象或具体 GUI 节点。崩溃根因仍未定位。

## 0.1.5.0 重复恢复精简构建

运行日志中，一次恢复 2560×1440 的 ResizeBuffers 调用与运行环境重建完成之间相隔约 15.9 秒。同期间 MotionFocus.fx 编译耗时 16.277 秒，编译结束后才继续重建，随后又发生一次同尺寸的 ResizeBuffers。ReShade 6.6.1 的重置流程会等待效果编译线程结束，和这次停顿的时间线吻合。此前的 Dtor 回调崩溃属于另一个尚待定位的问题。

精简构建保留已成功触发热切换的临时尺寸与完整显示器尺寸请求。原模式已是无边框时跳过模式恢复的空等待；对最终恢复，只有实际矩形、完整 WindowPlacement 和交换链状态分别吻合时才省去对应操作。存在待处理尺寸请求时不跳过，必要的窗口模式、最大化与位置恢复仍保留。没有实际恢复操作时省去最后一次固定等待。原无边框且状态已经完全恢复的路径，固定等待可由 4.8 秒降为约 3.2 秒，不含游戏与 ReShade 内部耗时。

0.1.5.0 编译成功，无编译警告。独立源码复核检查了窗口恢复、取消和异常处理，未发现恢复路径退化。此次修改针对重复恢复和切换等待。

操作状态改为结束后显示最终结果，避免长期停留在“桥接更新已提交”。刷新期间不显示中间状态；结束后保留 ok applied 回执和窗口刷新结果，失败时给出原因。“写入并刷新生效”只在流程结束后通知结果，单独“写入配置”仍通知保存结果。实际 DLSS 输入尺寸继续通过 OptiScaler 菜单查看。
